Syllabus Checker

AI tools & strategy

A submit-and-check tool that verifies a syllabus against the district and program requirements, replies to the faculty member instantly, and logs every submission in one place for the department.

Open the tool

Goal

Make sure every syllabus meets the MCCCD required elements and any program requirements before the term starts, without a person hand-checking each one, and give faculty a clear answer right away.

Audience

Faculty submitting a syllabus, and the department that collects and verifies them.

Process, how it works

Faculty submit through the department’s existing Google Form, exactly as they do today. Nothing about their habit changes. That submission fires a check against the MCCCD Regulation 3.6 required elements, the program’s own additions, and the approved seat-hours and interaction language. The instructor gets an email back within seconds: a sign-off if the syllabus is complete, or the precise list of what is missing, with the correct approved wording included in the email so there is nothing left to go hunt down.

Two audiences, two different outputs

This is the design decision that makes it useful rather than annoying. Faculty need to act, so they get an email telling them what to fix. The department needs to monitor, which is a completely different job, and forty copies of forty reports is not monitoring, it is drowning.

So the check writes its result straight back into the form’s existing response spreadsheet, as status columns colored by state. One tab, sortable: complete, missing items, unreadable, not yet submitted. The person tracking compliance opens a spreadsheet they already have and sees the whole term at a glance.

Why there is no API, no server, and no vendor

It runs on Google Apps Script, inside the Workspace account that already owns the form. That means no OAuth app, no client secret, no backend to host, nothing to license, and nothing to pay for. It also means the department owns it rather than any one person, so it keeps running when people move on.

The approved language is read live from the department’s own reference document on every single run, never copied into the code. When the wording is revised, the checker is current the same minute. There is no stored copy to drift out of date, which is the way every compliance checklist ever written eventually fails.

No data collected. Not by me, not by anyone.

Nothing is uploaded to a third party. There is no external service, no database, no logging, and no vendor sitting in the middle. A syllabus never leaves the district’s own Google account, and no student data is involved at any point, because a syllabus contains none. The tool reads a document and writes an email. That is the entire data footprint.

And it is read-only. It never edits anyone’s syllabus. It reports, and a human decides. That boundary is deliberate: nobody should discover that an automated process quietly rewrote a document they are accountable for.

The compliance checks use no AI, on purpose

“Does the approved statement appear verbatim” is a string comparison, not a judgment call. A language model would be actively worse at this, because it might decide a paraphrase counts. On something an accreditor reads, deterministic beats clever, and a confident wrong answer is the worst possible outcome. AI is reserved for the genuinely fuzzy checks, and the tool delivers most of its value without them.

The honest limit

Google Docs and Word files read cleanly. PDFs do not. Text extraction from a PDF is imperfect, and a verbatim check against imperfectly-extracted text throws false failures, which is worse than no check at all because it teaches people to ignore the tool. So it says so out loud: a PDF submission gets flagged as possibly unreliable, with a note to resubmit as a document. The real fix is a policy conversation about accepted formats, not a code one.

Status

Prototype, and honest about it: this is not live yet. The interface and the check logic are built, but it has to be installed on the department account that owns the submission form, which is a conversation to have with the administrator who runs it, not something to switch on unilaterally. Until then this is a working demonstration of the workflow.
