Campground Finder

Product requirements

OverviewSample runProduct requirementsWayfinder

Both halves are built. The form lives in the Wayfinder builder and the watcher is a scheduled agent, currently switched off.

1. Summary

Watches one campground for a cancellation and tells me the moment a site opens, because the good ones are booked eleven months out and the only way in is someone else’s change of plans.

2. Goal

Surface a cancellation at one named campground fast enough to act on it, with no manual checking.

3. Users and context

A single person planning a specific trip. Not a marketplace, not a service, and not something that books on anyone’s behalf.

4. How it works

A search form takes an area, nights, optional dates, and filters, then opens a live Recreation.gov search. Separately, a scheduled agent checks target campgrounds each morning, at the hour the booking platforms release sites that people cancelled overnight.

The design principle is that it removes every step except the card. When a watched site opens, the calendar notification links straight to the exact booking page with the campground and the site already identified. It does not book, and it should not, but nothing is left to figure out at the moment it matters.

5. Data, privacy, and governance

No accounts, no user data, no payment details. It reads publicly available availability and writes to my own calendar. It never holds a credential for a booking site and never completes a reservation.

6. Build and portability

Single purpose and configurable by campground and date range. Booking sites change their markup, so the fetch layer has to be replaceable without touching anything else.

The watcher cannot live on the website. A static page on public hosting cannot run on a schedule, so the watcher is a scheduled agent that runs elsewhere and writes to a calendar. That constraint is why the tool is split in two: the form is a page, the watcher is an agent, and the calendar is how they meet.

7. Handoff to Wayfinder

One direction only. After a reservation is confirmed by hand, the dates and location pass to Wayfinder, which owns the trip from there. Wayfinder never calls back into this tool.

8. Pilot and testing

One real trip. It either got the site or it did not, which is a cleaner success measure than most software gets.

9. Definition of success

A booking obtained that manual checking would have missed.

10. Open questions and risks

Which reservation systems to support. How often a check can run without being rate limited or blocked. Whether the terms of the booking site permit automated checking at all, which needs answering before anything is built.

11. Roadmap

Both watchers are disabled and can be switched back on for a trip. The open work is generalizing the watcher so a campground is a setting rather than a separate scheduled task per site. Two tasks for two campgrounds does not scale, and one of them is even named for the wrong park.

This specification was pulled out of the Wayfinder PRD, where the watcher appeared as a companion feature. It is a separate tool with a separate job, and the handoff to Wayfinder happens once, after a booking is confirmed.
