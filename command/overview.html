Project Dashboard

Case study · Personal Projects

OverviewDashboard

Every project in this portfolio, run as a real product backlog, so priority, progress, and what is actually blocked live in one place instead of scattered across a calendar.

Goal

Keep the whole portfolio on a board instead of in someone’s head. Every project gets a product goal, a release plan, a sprint backlog, its impediments, a definition of done, and a product backlog, so what is actually in flight and what is quietly stuck are visible at a glance.

The rule the whole board enforces: a project is not done when it is built. Design, build, launch or pilot, then measure. Nothing here is finished until there is evidence it worked, and every card shows how far along that arc it really is. Everything on it is a prototype or in testing. Nothing is in production, and the board says so.

Audience

A personal learning tool first, and also the honest answer to “how do you run your projects.”

Process

Built as practice for the Professional Scrum Product Owner (PSPO I) exam: rather than rehearse the vocabulary on invented case studies, the board runs the real work in this portfolio. Every project is a product with a named product owner, so the Scrum terms have to be used correctly on real work, learning a language by having to speak it about something real.

The products are ranked, and cards open one at a time. The Scrum vocabulary is defined on the dashboard itself, at the top, so the terms sit next to the work they describe. The header counts are computed from the data rather than typed, because a dashboard that lies about its own numbers is worse than no dashboard.

Technology

  • A single self-contained HTML file: structure, styles, and vanilla JavaScript in one document, with no framework and no build step.
  • One project list is the single source of truth. Every card, roadmap, milestone, and header count is rendered and tallied from it at load, so the summary numbers cannot drift from the underlying data.
  • Each project is modeled as a backlog item carrying its stage, roadmap milestones, blockers, a north-star measure, and links.
  • Client-side only: no backend, no external calls, and nothing stored off the page.
  • Published to GitHub Pages with a noindex, nofollow tag and left unlinked, a working self-management view rather than a portfolio piece.

Outcomes

The whole portfolio sits on one board instead of in someone’s head, so priority, progress, and real blockers are visible at a glance rather than scattered across a calendar. Because every header count is computed from the underlying project list rather than typed, the summary cannot drift from the work it describes.

Running real projects through Scrum artifacts, product goal, release plan, sprint backlog, impediments, definition of done, turned Professional Scrum Product Owner (PSPO I) preparation into practice on live work rather than rehearsal on invented cases. The board also enforces the standard it was built to teach: a project is not done when it is built, only when there is evidence it worked, and every card shows where on that arc it really is.

Status

In use, and refreshed as work moves. It is a personal working tool, deliberately unlisted and set to noindex. Nothing on the board is presented as a finished product; each card states its own stage, and the arc from design to measured evidence is the point.
