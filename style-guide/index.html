Heading & footer style guide

A proposal to lock down two things that have drifted across the portfolio: the section headings on content pages, and the return link on tool pages. Nothing on the live site is changed yet. Tweak any value and it becomes the rule.

GoalOne documented heading system (real, accessible H1 / H2 / H3) and one tool footer, so every portfolio page reads as the same hand and passes a heading-order check.

AudienceYou, building and maintaining the site, and a hiring manager or screen-reader user auditing it.

ProcessPick the tag by where it sits in the outline, never by size. Then style H2 and H3 exactly as shown below. Apply to overviews and content tabs (PRDs and doc tabs). Tools and courses keep their insides and only adopt the footer.

Page types (decide this first)

Two families: website (content) pages and tool pages. Stapling the heading system onto a tool is the most common mistake, so pick the type before building.

The green eyebrow leads with the piece’s type: every page is either a Case study (professional or study work) or Personal (a personal project). That type word comes first, followed by every category the project belongs to, drawn from this set and kept in this order: AI Tools & Strategy, Learning Design, UX Design, Teaching/Program Design, Personal Projects. So an eyebrow reads, for example, “Case study · AI Tools & Strategy · UX Design” when a project belongs to both of those categories. AI Tools & Strategy leads the categories (Michelle’s top targets are AI builder and AI strategy). Learning Design is course/experience design; Teaching/Program Design holds program-level work and classroom teaching.

Overview page, content

The project’s front page, and the only page with a hero image and with Goal / Audience / Process. Order: header, H1 (project name), green category eyebrow, tabs, serif-italic lead, hero image, then Goal / Audience / Process as H2 with H3 nested, a status line at the bottom, footer.

Secondary tab page, content

Any tab other than the overview (The Case, a doc tab). Identical to the overview minus the hero image. Carries its own H2 / H3 sections, never Goal / Audience / Process. H1 matches its tab label, or a bit longer.

PRD page, content with a fixed flow

A secondary page, but every PRD uses the same numbered section flow so they all read alike. H1 and browser title: “Product Requirements Document, [Project].” The standard H2 flow:

  1. Summary
  2. Goal
  3. Users and context
  4. How it works
  5. Data, privacy, and governance
  6. Build and portability
  7. Pilot and testing
  8. Definition of success
  9. Rollout
  10. Open questions and risks
  11. Roadmap

Most PRDs already follow this. The Syllabus Checker PRD is the current outlier and should be brought onto this flow.

Tool page

The interactive tools (CopaMigo, Render, Dial Your Course, Syllabus Checker, Wayfinder), the built courses (Data Science, Light & Lasers, the AVC pages), the family pages (Focus, Flow, Soar, Summer Work, Devan), and the newsletters (Rough Cut, the Flow volumes). These get NONE of the heading system: no H2 / H3, no eyebrow, no Goal / Audience / Process, no anatomy. They keep their own interface and do their job. The only shared element they adopt is the standardized return footer link. If a heading ever gets stuck on one (Flow, for example), remove it.

Language and content

  • No ornamental drift, body text by default. Do not invent type or box styles. A caption (small muted grey) is only for an actual image or chart caption. The ONLY sanctioned callouts are the grey rail box and the green box (see Callout boxes), used sparingly to flag something important, never purple, never nested. Everything else is plain body text. When in doubt, use body text.
  • Bold is functional, not decorative. Use bold only for the short lead-in term of a list item (a label followed by its explanation, like “Backward design.” then the definition) or to mark a genuine key term, sparingly. Never bold whole sentences or use bold for ornament. Headings carry emphasis, not bolded body text.
  • Voice. Formal and professional, grounded in learning science. Concise and to the point, conceptually sharp, never padded. Use precise instructional-design and UX vocabulary where accurate.
  • Title length. H1 fits on one line where possible, two lines maximum, aim under about 45 characters. Tab labels are one to three words.
  • Call out all technology by name. Name every real tool: the Adobe apps (Illustrator, Photoshop, After Effects, InDesign), Figma, Canvas, vanilla JS, the model and API, localStorage, IMSCC, and the Google Workspace tools actually used (Docs and Drive folders for group work, Sheets, Forms, Apps Script). Google is a tool like any other, name it. Never say “design software” or leave a real tool unnamed.
  • Cite what needs citing. When a page uses external material, a framework, a study, or a course from another institution, attribute it by name and link the source. A course referencing Colorado School of Mines, for example, says it came from Mines and links the page it was found at. Follow the Grounding pattern: source, publication, live link.
  • Assessment and outcomes. Do not include an Assessment or Outcomes section if there is genuinely nothing to report, but make a real effort to find something honest to include (a planned measure, a pilot metric, a usability result).
  • Status at the bottom. Place status last, before the footer, and frame it toward the furthest honest state of completion so the work never reads as unfinished. Stay honest, never imply production a tool has not reached.

Layout and margins

Body text has a reading measure and stops part way across (max-width about 700 to 720px), left-aligned at the page’s left margin. It never runs the full width of the page. The header text and every rule line (header rule, tab rule, section dividers, footer rule) DO run the full width of the page band, so a rule never stops at the narrow text column. Tools are the only place content may span full width.

The three heading levels

Levels follow document structure. The page has one H1 (its title). Top-level sections are H2. Anything nested inside a section is H3. Choose the tag by the outline, then the look is automatic.

Overview page anatomy

Every overview runs in this exact order, top to bottom. Nothing floats loose between the pieces.

  1. Top bar, the identical site header (name + rule line) on every page.
  2. H1, the project title.
  3. Type-and-category eyebrow, green uppercase. It leads with the type, Case study or Personal, then every category the project belongs to, in the index-page order.
  4. Tabs, underlined plain text, active tab underlined in plum. No pills.
  5. Description paragraph, a few sentences on what the project is, set in serif italic as the page’s lead.
  6. Hero image.
  7. Goal, Audience, Process and any other sections, as H2, with H3 nested inside.
  8. Status, at the bottom, framed toward completion.

Active navigation state (lit current page)

The header and footer always show where you are. The word for the current page is lit plum and underlined, the same way the in-page tab bar underlines its active tab. Michelle Blomberg (the name, top left) is the Home link: its normal state is black, and it lights plum and underlined only on the home page. So on the home page the name is lit; on the Work section (the /#work anchor) and on every project or overview page, Work is lit; on the About page, About is lit. The footer Home, Work, About behave identically. Nothing is lit plum by default, only the current page. Clicking Work always resets the work grid to All, so every card shows.

Lit-state CSS

Implementation, LOCKED: one identical self-configuring snippet lives at the end of every page, just before the closing body tag, marked nav-active v1. It reads the URL and sets the lit word in both the header and footer, so it never has to be tuned per page and can never drift. Do not hand-add an active class to one page. Paste the nav-active v1 block (the canonical copy is at the bottom of index.html) and it configures itself.

The name is a nav item, not a logo

The name at top left (“Michelle Blomberg”) is the Home link and must render exactly like the Work and About nav links: same size, same weight, same line-height, same distance from the header hairline. It is never bold, never larger, and never carries its own underline. Its only underline is the shared header hairline that runs under the whole bar, identical to Work and About. It is muted grey by default and turns plum only on the home page (its lit state is color alone, no extra underline).

Typefaces, never faked

Two families only: Lora (serif) for headings, titles, card names, and serif-italic leads; DM Sans for everything else. The hard rule: never let the browser synthesize a weight or an italic. If any element uses Lora italic 600, the page must actually load Lora italic 600. Faux-bold and faux-italic (using a weight or style that was not loaded) are not allowed anywhere.

Every page loads the full range it might use, so nothing is ever faked. Use this exact Google Fonts request on every page:

Font request, LOCKED (paste on every page)

https://fonts.googleapis.com/css2?family=Lora:ital,wght@ 0,400;0,500;0,600;0,700;1,400;1,500;1,600;1,700 &family=DM+Sans:wght@300;400;500;600;700&display=swap

Lora loads upright and italic at 400/500/600/700; DM Sans loads 300 through 700. If a new weight or style ever gets used, add it to the request first. Never ship a page that styles text in a cut it did not load.

Lists

Real bulleted or numbered lists, never boxes or left-border bars standing in for bullets. Bullet markers are green and sit at the left margin, with a hanging indent so wrapped text lines up with the first word. Ordered lists use plain body-text numbers so multi-digit numbers align cleanly. Prefer bullets; use numbers only when order matters. Labeled list: when each item is a term and its explanation (a definition or question-and-answer pattern), open the item with the term in bold, then the explanation in plain body text on the same run. That is the one way to do a term-and-explanation list. A single important callout can use the grey rail box instead (see Callout boxes), but a list of items uses bullets, not rails.

  • Backward design. Outcomes first, then evidence, then instruction, so a wrapped line as long as this one lines up under the word “Outcomes,” not under the bullet.
  • Constructive alignment. Outcome, activity, and assessment cohere rather than merely coexist.
  1. Numbered only when sequence matters, like the ordered steps of a process.
  2. Plain body-text numbers, aligned in one column, that handle 10 and 11 cleanly.

Callout boxes

Use a callout only to flag something important, sparingly, never the whole page and never nested. Two treatments, never purple (a box is not a link).

Grey rail box

A grey left rule beside the content. Good for a question-and-answer or a term and its note. The first part (the question or term) is body text, bold if it is a label; the second part (the answer) may be grey, at the same size as body text, never smaller.

Why synthetic testers over humans? Volunteer capacity is the constraint. AI testers run the same scenarios in parallel, so coverage scales past what the volunteers can carry.

Green box

A filled pale-green callout with a green border, for one short important note. Plain body text inside.

No student data, ever. Every tool is built to the no-PII, test-account model.
