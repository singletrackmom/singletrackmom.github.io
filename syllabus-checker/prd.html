Syllabus Checker

Product Requirements Document · Automated syllabus compliance review

A read-only workflow that checks a submitted syllabus and reports what is missing

Version 0.2 · Status: Complete. Awaiting installation on the department account

Michelle Blomberg · Residential Faculty, Digital Media Arts · Glendale Community College

1. Executive Summary

The Problem

Every term, faculty submit a syllabus through a department Google Form. Someone then reads each one by hand against the MCCCD required elements, the program's own additions, and the approved seat-hours and interaction language, which has to appear verbatim not paraphrased.

That review is slow, it is inconsistent depending on who does it and how tired they are, and the feedback loop is long. A faculty member can discover in week six that their syllabus was missing a required statement in week one. Meanwhile the person tracking compliance has no single view of who is done and who is not.

The Solution

The existing form fires an automated check on submit. The instructor gets an email within seconds listing exactly what is missing, with the correct approved wording included so there is nothing to go find. The department gets status columns written back into the response spreadsheet they already have, so compliance is one sortable tab rather than an inbox.

It is read-only. It never edits anyone's syllabus. It reports, and a human decides.

1.1 Audience

UserNeedOutput
Faculty memberTo know what is missing, and to fix it without hunting for the correct wording.An email with the specific gaps and the approved language, ready to paste.
Department administratorTo monitor compliance across all sections.Status columns in the existing response spreadsheet. One sortable tab.

This split is the central design decision. Faculty need to act so they get a message. The administrator needs to see the whole term so she gets a dashboard. Emailing the administrator a copy of forty reports is not monitoring, it is drowning, and it is the mistake most compliance tools make.

2. Architecture

2.1 Why Google Apps Script

The department already runs the submission form in Google Workspace on a college account. Apps Script runs inside that Workspace, as an authorized user, with access to Docs, Drive, Sheets, and Gmail already granted.

The consequences are the entire architectural argument:

  • No OAuth app. No consent screen, no client ID, no verification process.
  • No client secret and therefore no backend needed to hold one. A browser page has nowhere safe to keep a credential; Apps Script sidesteps the problem entirely.
  • No server to host no hosting bill, no uptime to maintain.
  • No CORS no proxy, no vendor.
  • The department owns it not any one person. It keeps running when people move on, which is the failure mode of every tool built on someone's personal account.

2.2 Flow

  1. Faculty submit through the existing Google Form. Nothing about their habit changes.
  2. An onFormSubmit trigger fires.
  3. The script reads the approved-language document live (see 2.3) and extracts the submitted syllabus text (see 4.1).
  4. It compares, builds findings, and emails the instructor.
  5. It writes status columns back into the form's response sheet for the administrator.

2.3 The approved language is read live, never copied

The script reads the department's reference document on every single run. It does not store a copy.

This is not a minor implementation detail. A stored copy going stale is how every compliance checklist ever written eventually fails. The department revises the wording, nobody updates the checker, and the tool starts confidently approving syllabi against language that is no longer current. Reading live means the checker is correct the same minute the document changes, and there is nothing to maintain.

3. Data and Privacy

  • No data is collected. No database, no logging, no analytics, no retention.
  • No third party. No external service, no vendor, nothing outside the district's own Google tenant.
  • No student data, at all. A syllabus contains none. There is nothing here to protect because there is nothing here.
  • Read-only by design. The script never edits a syllabus. Nobody should discover that an automated process quietly rewrote a document they are accountable for.
  • The only thing written anywhere is a status value in a spreadsheet the department already owns, and an email to the person who submitted.

4. Requirements

4.1 Reading the syllabus, and the honest limit

FormatReliable?How
Google DocYes. Native.Read directly via DocumentApp.
Word (.docx)Yes.Convert via Drive, read, discard the temp copy.
PDFNo.Convert via Drive. Text extraction is imperfect.
Syllabus+ PDF URLNot yet supported.Needs a fetch-and-parse step. See section 7.

The PDF problem is real and must be surfaced, not buried. A verbatim string check against imperfectly-extracted PDF text produces false failures. A checker that fails people incorrectly will be ignored, and correctly so.

Requirement: when the submission is a PDF, the report states plainly that extraction may be unreliable and tells the instructor to resubmit as a document if the report flags language they know is present. The tool must never fail someone silently and confidently.

The real fix is policy, not code: ask the department to accept Google Docs and Word. That is a conversation, and it is worth having.

4.2 Compliance checks

Submission deadlineComputed from the class start date: the Friday of the first week.No.

4.3 Why the compliance checks use no AI, on purpose

"Does the approved statement appear verbatim" is a string comparison, not a judgment call. A language model would be actively worse at this because it might decide a paraphrase counts as a match. On something an accreditor reads, a confident wrong answer is the worst possible outcome.

Deterministic beats clever here. AI is reserved for the genuinely fuzzy elements, and the tool delivers most of its value with the model turned off.

4.4 Normalization (the difference between a tool people use and one they hate)

A verbatim check that fails on a curly apostrophe is useless. Before comparing, normalize: curly quotes to straight, em and en dashes to hyphens, non-breaking spaces to spaces, collapse all whitespace, lowercase. Formatting noise must never cause a false failure.

4.5 The report

  • To the instructor: an email. Green if complete, red if not. Each finding names the problem and, where relevant, includes the approved wording ready to paste. No hunting.
  • To the department: four columns written back into the existing response sheet, check status, missing items, file type, checked-on date. Status cell colored by state (solid colors, never gradients).
  • Optional weekly digest: a summary of what is still outstanding.

5. Design Principles

  1. Read-only. Report, never rewrite. The human is accountable, so the human decides.
  2. Deterministic where it matters. Compliance is string matching, not model output.
  3. Never fail someone silently or incorrectly. If the tool cannot read a file, it says so and checks nothing rather than guessing.
  4. Read the source live. Never store a copy of a document that someone else maintains.
  5. Fit the existing habit. Faculty already use the form. Do not make them learn a new thing.
  6. Two audiences, two outputs. Acting and monitoring are different jobs.

6. Known Limits

  • PDF extraction is unreliable for a verbatim check. Surfaced, not hidden. See 4.1.
  • Syllabus+ PDF URLs are not yet read. The form accepts them; the checker cannot follow them yet.
  • Modality is not asked on the form so RSI applicability is inferred from the syllabus text. When it cannot be determined, the tool says so rather than failing someone. Adding a modality question to the form would remove this guesswork entirely and is the cheapest single improvement available.
  • Form field titles are matched by exact string. Reword a question on the form and the script silently reads nothing. This is fragile and needs a validation run.
  • Seat-hour profiles are department-specific. Currently GCC Art & Humanities.

7. Status and Next

The interface and the check logic are complete. Activation requires installation on the department account that owns the submission form, which is an administrative authorisation rather than a technical step. The remaining work is a conversation, not a build.

Next, in order:

  1. Secure authorisation from the department administrator. This is the operative dependency, and it is not a technical one.
  2. Verify the form field titles against the live form, character for character.
  3. Add a modality question to the form (online / hybrid / in person). Removes the RSI guesswork.
  4. Ask the department to accept Google Docs and Word and to discourage PDF. This makes the whole tool dramatically more reliable and costs nothing to implement.
  5. Run it in report-only shadow mode for one term: check, log, but do not email faculty. Compare against the manual review to measure accuracy before anyone trusts it.
  6. Add the Syllabus+ URL fetch.
  7. Add the fuzzy MCCCD element checks last, clearly labeled as suggestions.
