1. Summary

Faculty who take professional development seriously (AI literacy, community of practice work, new course development, conference proposals) have no purpose-built place to keep it. Resources sit in bookmarks across three browsers, notes sit in a separate app, deadlines sit in a calendar nobody opens, and the overhead of managing the system consumes the time meant for learning.

Cultivate consolidates that into one zero-dependency hub: six linked HTML pages, no backend, no login, no build step. It holds the professional development roadmap with real target dates, a completed-activity log, a UX reference toolkit, a conference proposal page, and a curated RSS feed of AI-in-education news routed by a keyword classifier. It loads and works offline, which is the reason it exists. It was built to be used on an iPad in the air and in rooms with no reliable wifi.

The design premise is connectivism: a personal learning environment where the network of people, tools, and sources is the point, rather than a closed app that owns the learner’s work. It is also a reference architecture. Every variable that makes it Michelle’s (audience, goal type, time horizon, deadline set, resource types) can be swapped to rebuild the same tool for a different person, department, or cohort.

Honest framing: Cultivate was the first AI-assisted build in this portfolio. It is in daily personal use and stable, but it is a single-user prototype. It has never been piloted with a cohort and nothing here is in production.

4. How it works

Cultivate is six interconnected HTML pages sharing one design system, one header, and one navigation pattern. Each page loads independently.

PageWhat it does
Resources hubEntry point. Classified news feed, resource cards, progress bar, daily reading button strip, link into the professional development dashboard.
Professional development planNine-priority roadmap with real target dates. Checkbox tasks, progress bar, collapsible phases, deadline badges.
Professional development logActivity log fed automatically by hub checkboxes. Category badges, summary stats, CSV export. This is what a faculty evaluation plan needs and what nobody keeps by hand.
UX toolkitReference page for UX and design tools, vocabulary, practice projects, and newsletters.
Conference pageSingle-proposal working page: date urgency banner, session abstract, learning outcomes, preparation list.
Context prompt blockA collapsible block in the hub footer with a one-tap copy button. Pasting it into a new AI session restores project context (tools, goals, preferences, design system) without re-explaining anything.

The news feed

The feed is the only technically complex part of the tool, and it is the part most likely to break, so it is worth stating plainly.

  • A shared pool of curated RSS sources (currently 51, trimmed from 62 when six high-traffic outlets moved to a daily reading button strip) is fetched for every refresh. No source is tied to a single tab.
  • A keyword classifier routes each article to the tab it best matches. A home tab acts as tiebreaker only. The top articles per tab are displayed.
  • RSS endpoints do not support cross-origin requests, so fetches run through a three-proxy waterfall (rss2json, then allorigins, then corsproxy). If all three fail for a source, that source is skipped silently and the feed degrades rather than breaking.
  • The classified pool is cached to localStorage with a 24-hour expiry, so the feed stays readable offline after the first successful load.

The proxy waterfall is the known weak point. Public CORS proxies are third-party services with no uptime guarantee, and this is the first thing that would have to change for an institutional deployment (see section 6).

5. Data, privacy, and governance

Cultivate collects nothing. There is no account, no form, no analytics, and no transmission of user data anywhere.

DataWhere it livesStatus
Checkbox state, notes, activity logBrowser localStorage on the user’s own deviceNever leaves the device. Not transmitted, not synced, not backed up.
Cached news articlesBrowser localStorage, 24-hour expiryPublic article metadata only. No user data attached.
Personally identifiable informationNot collectedNo name, no email, no institutional ID, no login.
Student dataNot applicableCultivate is a faculty tool. No student data of any kind enters it, so no FERPA exposure exists.
Outbound requestsPublic RSS endpoints via public CORS proxies, Google FontsThe proxies see the requested feed URL. They receive no user data because none exists to send.

This matters for district review: a tool that collects nothing has nothing to govern. Any future feature that changes that (a shared team instance, a synced log, a saved-resource backend) crosses a line and would need a data agreement before it ships. Section 10 flags each one.

6. Build and portability

What it is built with

  • The front end is HTML5, CSS3, and vanilla JavaScript, with no framework, no build step, no package manager, and no dependencies to install or patch.
  • The design system is a set of CSS custom properties in a single root block shared by all six pages: Lora for headings, DM Sans for everything else, 15px base.
  • Persistence is the browser localStorage API. There is no database.
  • There is no authentication, because there is nothing to log into.
  • The feed is a client-side RSS fetch through three public CORS proxies in sequence, with a keyword classifier and a 24-hour local cache.
  • Hosting is GitHub Pages: static files, deployed by pushing to the repository.
  • No AI model is called inside Cultivate today. AI was used to build it, not to run it, and article routing is a keyword classifier rather than a model.

Can it run on district infrastructure

Yes, with one qualification. The six pages are static files with no server-side requirement, so they will serve from any web host the district already runs, from a Canvas page, or from a shared drive opened locally in a browser. Nothing about the tool is tied to GitHub Pages.

The qualification is the news feed. It depends on three public CORS proxies that the district neither controls nor has an agreement with. For an institutional deployment those would be replaced by a small server-side fetch endpoint on district infrastructure that pulls the feeds and returns them as JSON. That is the single largest change required, and it is the one thing that turns a fully static tool into one with a (minimal) backend.

Is the AI model swappable

The question is currently moot and would remain easy to answer if it stopped being so. No model is called today. The planned AI features (article summarization, resource recommendations, plan drafting) would sit behind a single fetch function, which is the pattern already used in Render. Swapping Claude for Gemini or another provider means changing the endpoint, the authentication header, and the response shape in that one function. Prompts are provider-agnostic plain text. No prompt would contain user data, because the tool holds none.

What porting actually requires

ChangeEffortNote
Rehost the static filesLowCopy the directory. No build, no configuration.
Replace the CORS proxies with a district fetch endpointMediumRequired. Removes the third-party dependency and the uptime risk.
Rebrand and re-key contentLow to mediumSwap the design tokens, the deadline set, and the resource lists (section 3 variable map).

7. Pilot and testing

Cultivate has not been piloted. It has been used continuously by one person (its author) since v1.0, which has surfaced real defects and driven three releases, but that is dogfooding, not evaluation. A pilot would be the next step and has not been scheduled.

ElementProposed
Participants6 to 10 faculty from the campus AI community of practice, mixed disciplines and mixed technical comfort. Recruitment through the Center for Teaching, Learning and Engagement.
PeriodOne semester, with a setup session in weeks 1 to 2, a mid-point check in week 8, and an exit interview in weeks 15 to 16.
What is measuredWhether participants can install and personalize their own copy without help. Whether they still open it in week 8 and week 15. Whether the activity log produces evidence they can actually use in a faculty evaluation plan. Which pages go unused. Feed reliability, logged as failed source fetches per week.
MethodTask-based usability sessions at setup, a short survey at each checkpoint, and exit interviews. No usage telemetry is collected from the tool itself, which is a deliberate cost of the no-data design and means self-report carries the load.
Not measuredLearning outcomes. Cultivate organizes professional development, it does not deliver it, and claiming otherwise would be overreach.

8. Definition of success

Cultivate reaches 1.0 when it has passed a pilot and is cleared for rollout. These are the thresholds that decide it.

ThresholdBar
Independent setupA participant with no coding background can stand up and personalize their own copy in one session, without the author touching it.
RetentionA clear majority of participants are still using it at the end of the semester, not just at week 2. If most abandon it, the tool has failed regardless of what it does.
Real outputParticipants can point to something they took out of it: a professional development log they submitted, a deadline they met because it was visible, a resource they used.
Feed reliabilityThe feed loads on every attempt during the pilot period, with a district-hosted fetch endpoint replacing the public proxies before rollout. Silent source failures are logged, not hidden.
Offline behaviorEvery page loads and the cached feed reads with no connection, on both iPad and laptop, verified in testing rather than assumed.
Governance clearanceConfirmation from district review that a tool collecting no user data requires no data agreement, in writing, before anyone else is asked to adopt it.

Failing the pilot is a real outcome. If faculty will not maintain a personal copy, the correct conclusion is that this architecture serves one motivated user well and does not generalize, and it stays a personal tool.

9. Rollout

If the pilot passes, rollout proceeds in steps, each one a decision point rather than a formality.

  1. Harden the feed by replacing the three public proxies with a district-hosted fetch endpoint, before anyone outside the pilot is asked to use the tool.
  2. Write the adaptation guide: document the variable map (section 3) as a short, plain guide so a new user can rebuild the tool for their own goals without reading the source.
  3. Publish a template copy, a stripped, content-free version of the six pages, forkable, with a starter design token set and an empty roadmap.
  4. Offer it through the Center for Teaching, Learning and Engagement and the campus AI committee as an optional tool, with one setup workshop per semester. Adoption stays voluntary, because the tool is worth nothing to a faculty member who does not want it.
  5. Evaluate district reach after two semesters of campus use: whether other colleges want it, and whether the sensible unit is a shared instance (which requires accounts, a backend, and a data agreement) or continued personal copies (which require none of that). The default is personal copies.

10. Open questions and risks

Question or riskPriorityPosition
Public CORS proxies are a third-party dependency with no uptime guaranteeHighThe main technical risk. A district-hosted fetch endpoint is the fix and is a rollout prerequisite.
localStorage is device-specific and disappears if browser data is clearedHighAccepted for a single-user prototype, but a user who loses a semester of log entries loses the tool’s main value. An export path (CSV exists for the log; the rest does not) needs to cover everything before a pilot.
Adding a resource requires editing the HTML by handHighThe biggest usability defect. A quick-save input (title, URL, category) is needed. Options: localStorage (offline, device-bound, free), or a spreadsheet-backed write (readable from any device, adds a dependency). Start with localStorage and keep the no-data line intact.
Does a keyword classifier route well enough, or does routing need a modelMediumKeyword routing is fast, offline-capable, and free. A model would classify better and would cost money, add latency, and break offline use. Not obviously worth it. Test before assuming.
Should Cultivate support teams or departmentsMediumThis is the boundary. Multi-user means accounts, a backend, and a data agreement, and it turns a tool that collects nothing into a tool that collects something. Do not cross it without a reason worth the cost.
Phone experienceLowResponsive but not designed mobile first. Works on iPad, which is the actual use case. Fine to leave.
